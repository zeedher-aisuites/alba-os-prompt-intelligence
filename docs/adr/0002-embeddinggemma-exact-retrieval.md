# ADR 0002: EmbeddingGemma adapters and exact pgvector retrieval

## Context

Stage 1 prepared nullable `vector(768)` data while preserving source
`embedding_text`. Stage 2 needs reproducible text construction, local embedding
generation, stale detection, positive evidence, rejected counterexamples, and
measured retrieval quality without introducing chat LLMs or agent frameworks.

The application must not bind its domain to Ollama or LangChain, and automated
tests must remain reliable when Ollama is not installed.

## Decision

Alba OS owns an async `EmbeddingProvider` protocol with provider name, model
name, dimensions, query embedding, and batch document embedding operations.
`OllamaEmbeddingProvider` calls the local `/api/embed` endpoint through
`httpx`; `FakeEmbeddingProvider` supplies deterministic token-hash vectors for
tests and diagnostics. Fake results are never treated as EmbeddingGemma
acceptance evidence.

The exact configured artifact is `embeddinggemma:300m`. EmbeddingGemma was
selected because it provides a compact
embedding-specific model with a full 768-dimensional output that matches the
Stage 1 schema. Ollama is used as the local runtime boundary. It keeps model
execution outside the application process and avoids coupling persistence or
retrieval code to Ollama-specific Python objects.

`EmbeddingTextBuilder` is pure and deterministic. It always uses the same
sections, collapses whitespace, includes empty optional sections consistently,
sorts and deduplicates tags, and hashes the final UTF-8 text with SHA-256.

The vector remains derived. A vector is stale when any of these is true:

- it is NULL;
- provider or model metadata differs;
- its source hash differs from the rebuilt text;
- `embedded_at` is NULL;
- the operator requests `--force`.

The indexer works in a caller-owned transaction, calls providers in batches,
uses `flush()` without `commit()`, and reports selected, stale, embedded,
skipped, and dry-run counts.

The vector and its provider, model, source hash, and timestamp are protected by
an all-or-none database `CHECK`. A row may be entirely unindexed or have a
complete vector provenance record; partial states are rejected.

Retrieval uses exact pgvector cosine distance:

```text
similarity = 1 - cosine_distance
```

Approved positive evidence and rejected failure patterns are separate public
service operations. In-review and NULL-vector examples are excluded. Results
never expose the raw vector.

No HNSW or IVFFlat index is created in Stage 2. Exact search establishes a
correctness baseline before approximate indexing introduces recall and tuning
tradeoffs.

## Alternatives

- The official Ollama Python library was not selected because the small HTTP
  adapter keeps the project contract explicit and adds no provider SDK.
- LangChain embeddings were rejected because they would couple a narrow adapter
  to a broader framework before any chain exists.
- A remote embedding API was deferred because local-first execution is a
  product requirement and would add credentials and data-boundary concerns.
- Qdrant was deferred because PostgreSQL already owns relational truth and the
  current dataset does not justify a second synchronized service.
- HNSW and IVFFlat were deferred until scale and benchmark evidence show exact
  scan latency is insufficient.
- Hashing only selected fields was rejected because every documented source
  field can affect semantic retrieval.

## Consequences

`httpx` is a runtime dependency. Real acceptance requires Ollama plus a
pre-pulled `embeddinggemma:300m` model; automated tests never download it.
Provider responses are rejected if the returned model differs, counts or
dimensions differ, values are non-numeric or non-finite, inputs are empty, or
JSON is malformed.

For the 64-row MVP rebuild, one caller-owned transaction remains open while
Ollama handles all HTTP batches. This preserves all-or-nothing rollback if a
later batch fails, at the cost of holding one database connection and snapshot
during model latency. This is accepted Stage 2 debt. A larger or concurrent
indexer must move to a two-phase workflow that generates vectors outside a
transaction and then rechecks source hashes before short transactional writes;
simply moving the HTTP call would introduce a stale-write race.

The Ollama request disables silent truncation. Oversized canonical documents
therefore fail explicitly; Stage 2 does not chunk or summarize them. Future
context management must preserve source hashes and document exactly what text
was embedded.

The deterministic 64-example demo dataset and twenty tagged evaluation cases
measure Recall@3, Recall@5, MRR, Precision@5, zero-result rate, and p50/p95
latency. Metrics must be generated by the runner and labeled with provider and
model. Fake-provider measurements are diagnostic, not model-quality claims.

Changing the embedding model without changing dimensions still makes every
vector stale through provider/model metadata. Changing dimensions requires a
new migration and column, regeneration from canonical source text, validation,
an optional new ANN index, a retrieval switch, and later removal of the old
column. Existing vectors must not be padded, truncated, or copied blindly.
